# 对 V1.0 方案的批判性评审

> 评审视角：大赛评委 + 全栈架构师 + Code Reviewer
> 结论先行：**方向和原则正确，但作为「一个业余时间有限的 Java 初学者两周内要跑通」的 MVP，过度设计了至少 60%**。

---

## P0 — 不解决就别开工

### 1. 合规红线被一句话带过

方案 12.3 写「按企业政策确认」，但这不是技术细节——**这是你有没有资格干这件事的前提**。

如果你用真实项目里的 RPG 源码 + DDS + 表结构 + 业务规则喂给 Claude Code（Anthropic 的 CLI/API，数据出境），劳动合同、保密协议、客户数据分级政策允许吗？

- 如果项目/客户方不让，后面所有设计都是废纸；
- 如果只能用自己造的 demo 代码，那「真实业务等价性」就彻底不存在了。

**这一条不解决，不要开始写任何代码。**

### 2. 第一版根本没有「业务等价性验收」，Acceptance Gate 是假的

整个方案的验收矩阵建立在「构建过 + 单测过 + 对照测试」上。但 AS400 → Spring Boot 迁移 90% 的坑在 RPG 隐式语义：

- `MOVE` 的左对齐/右对齐和小数位舍入；
- 子文件 SFL 的翻页逻辑；
- `EQALLOC` / `LLIST` / `READC` / `CHAIN` / `SETLL` 的游标行为；
- 日期世纪、数组维度、隐式数值截断。

这些东西**单测过了不代表业务对**。而第一版你既没有旧系统测试环境、也没有脱敏基准用例、也没有期望输出。所谓「业务对照测试」在 11.3 自己都承认做不到。

**那这个门禁真实能验的就只有「编译过 + 单测过」——这等于没验收。** 你交付的不是「迁移」，是「一段能跑的 Java 代码」。这个差距必须在方案里诚实写出来，不能包装成「端到端迁移」。

### 3. 「用户是谁」没定，MVP 形态就定错了

| 用户 | 你需要做的 |
|---|---|
| 自己简历/大赛作品 | 讲得清楚的架构图 + 一个能 demo 的截图 + 一个简单 shell 脚本，根本不需要 Python Orchestrator |
| 真在日常工作里提效 | 先做一个能帮你自己每天省 2 小时的小脚本，别推「数字员工平台」 |
| 团队内推广 | 你一个基层开发者没有这个授权，现在别碰 |

现在这份方案是按「企业级平台」写的，但执行主体是你个人。这个错位不解决，后面全是沉没成本。

## P1 — 过度设计，砍

### 4. Python Orchestrator + SQLite 5 表 + 15 状态机是 YAGNI

你自己写了「第一版单机、串行、单任务」。串行单任务意味着：一次只有一个活在跑，没有并发争抢、没有多 worker、没有分布式。这种场景下：

- 状态 = 一个 JSON 文件（`state.json`）
- 检查点 = 一个目录下的文件名（`01-analysis.done`、`02-plan.done`、`03-test.failed`）
- 事件 = 追加写 `events.jsonl`

就够了。

SQLite、5 张表、事件溯源、状态机合法性校验——这些代码量比迁移逻辑本身还大，而且你是 Java 都不熟的人，再手写一套 Python 子进程管理 + 信号处理 + 事务回滚，是双重学习负担。

**先让一个 shell 脚本跑通 3 个画面，再决定要不要上 Python。**

### 5. Claude Code headless 的权限边界是黑盒

方案说「权限最小化、命令允许列表、路径白名单」，但 Claude Code 本身是一个会自己跑 bash、自己读写文件的 agent。你怎么保证它：

- 不 `git push origin main`？
- 不 `mvn deploy` 到私有 Nexus？
- 不碰 worktree 之外的文件？
- 不 `rm -rf` 什么东西？

靠它自觉？靠 `.claude/settings.json` 的 `permissions.allow/deny`？靠 hooks？你真在 headless 模式下配过 `--allowedTools "Read,Edit"`、真的试过它会不会越权吗？

**这是整个方案能不能「无人值守」的命门**，4.1 的 `ClaudeRunner` 封装只写了 stdout/stderr/result_path，完全没写权限怎么锁。

### 6. 「独立审查 Agent」不独立

阶段 7 说「以新上下文读源码和代码」，但还是同一个 Claude。它会重复自己的盲点。真要独立：

- 要么换模型（GPT-5 / Gemini 交叉审一次）；
- 要么你自己花 30 分钟对着 diff 看。

比再调一次 Claude 有效得多。

### 7. WSL2 无人值守和你的现实冲突

你平时加班多，笔记本晚上合盖就睡，Windows 更新重启你也不知道。「后台无人值守」在你这台机器上物理不成立。

第一版就该改成：**下班前手动 `./run.sh MIG-xxx`，第二天早上看报告**。别和 systemd、休眠、Docker Desktop 搏斗。

## 真正的两周 MVP 长什么样

砍掉上面那些，第一版就 4 个东西：

```
migration-inputs/<screen>/
  workorder.yaml          # 工单
run.sh MIG-xxx            # 一键：建 worktree → 调 3 次 claude -p → mvn verify → 落盘
migration-runs/MIG-xxx/
  01-analysis.md/json     # claude 第一次：分析 RPG+DDS
  02-plan.md              # claude 第二次：迁移计划
  03-diff.patch           # claude 第三次：生成代码
  build.log / test.log    # mvn 真实输出
  report.md               # 你自己写的总结
```

- 状态 = 文件名存在与否
- 重试 = 你看到失败后手动再跑一次 `run.sh`
- 验收 = `mvn verify` 退出码 + 你自己 30 分钟看 diff
- 没有 Python、没有 SQLite、没有通知、没有监控指标

**试点画面必须满足**：

- 纯查询、无写操作
- 单 RPG 文件
- DDS ≤ 20 字段
- 表结构你看得懂
- 业务规则 ≤ 5 条
- 最好是你已经手工迁过一版的（这样你知道标准答案）

不要挑复杂画面，第一个是用来验证流程的，不是用来展示能力的。

## 你必须先回答的四个问题

1. **合规**：你用真实项目里的 AS400 代码做试点，还是自己在本机造一份 demo RPG？前者要先确认合规要求。
2. **客户**：这个数字员工是放进你简历/作品集，还是真打算在日常工作里用？
3. **对照**：你有没有任何途径（测试环境、脱敏样本、业务方口头讲）拿到旧系统对某组输入的真实输出？还是纯靠读 RPG 源码猜业务？
4. **试点画面**：你心里有候选了吗？是纯查询画面吗？你手工迁过没？

这四个答案定了，阶段 A 审计到底审什么、第一版代码写到什么粒度、哪些章节直接删，才能定。
